# ADR 0005: Zynq UltraScale+ support (3.0)

Status: **accepted** 2026-11-25 (the decisions under "Decided" are the maintainer's; the milestone plan may be revised as work proceeds). Builds on [ADR 0003](0003-bare-metal-and-rtos-platforms.md) and
[ADR 0004](0004-base-overlay-applications.md).

## Decided

1. **3.0 means Zynq UltraScale+ support**: what exists for the Zynq-7000 (three flavors, generator, CLI, libraries, applications) also works on Zynq UltraScale+ devices.
2. **Zynq-7000 stays supported, and everything stays backward compatible.** Keeping several versions of a file, and reorganizing the codebase to allow it, is acceptable.
3. **First board: Real Digital RFSoC 4x2** (`xczu48dr-ffvg1517-2-e`, as the vendor's board files say; those are published by Real Digital under Apache-2.0), over JTAG, with a private Ethernet cable to the host.
4. **A blank SD card** is available for bare-metal and later Linux validation.
5. **RF data converters start with a simple cable loopback.**

6. **The RF work is 3.1**, so that it does not hold up 3.0 (confirmed). Its loopback design is still built during the license window.
7. **The board definition files may be downloaded** from Real Digital's or PYNQ's public repositories.

## Scope

In 3.0: **Zynq UltraScale+ MPSoC and RFSoC** with a processing system, 64-bit (AArch64) on the Cortex-A53, one core. Only the RFSoC 4x2 is tested; an MPSoC board is expected to work after adding its board data and is not claimed.

Not in 3.0: Versal; FPGA-only UltraScale+ parts; the Cortex-R5 cores; running several cores (SMP); the PL-side DDR4; the 100 Gb QSFP28 port; USB, DisplayPort, SATA and PCIe.

## Backward compatibility: the promise and how it is enforced

The promise, for anyone using 2.7 with a Zynq-7000:

1. Every 2.7 command and flag behaves as before. The target family is **detected from the XSA**; no new flag is required.
2. A Zynq-7000 design generates the same crate as before, apart from the version it depends on and additive items. **Interface hashes do not change**, so `hardroxide update` works on existing crates.
3. Every public item of the 2.7 runtime crates keeps its path and signature: a program written against 2.7 compiles after changing `"2"` to `"3"`.
4. Linux, bare-metal and RTOS behaviour on the PYNQ-Z2 does not regress.

Enforcement (set up in step 0, run in CI unless noted):

- `cargo-semver-checks` of every library against its published 2.7.0 release.
- The Zynq golden snapshots and interface hashes, unchanged.
- A **frozen 2.7 project**: a crate generated by the published 2.7.0 CLI, with its programs, built against the 3.0 libraries.
- The existing QEMU Zynq tests; the PYNQ-Z2 board regression at every milestone (needs the board connected).

Two consequences of a **major** version number that is also backward compatible:

- Cargo treats `"3"` as incompatible with `"2"`: existing crates do not move to 3.x by themselves. They keep resolving 2.x until their owner changes the requirement. No 2.x maintenance branch is planned except for security fixes.
- A few public types in `hardroxide-hwh` and `hardroxide-gen` are exhaustive (`IrqRoute`, `Design`, `Instance`, `Platform`, ...). Adding a variant or a field to one would break code that matches or builds it. The rule: add **methods and new types** instead. Where that is
  impossible, the exception is recorded here and in the changelog, and never touches the crates a user's program links against.

## Codebase organization

One repository, one set of crate names, with the family-specific code **beside** the existing code, not mixed into it.

| Piece | Change |
|---|---|
| `hardroxide-ps7` | stays, same public API. It remains the home of the drivers for peripheral blocks both families have (Cadence UART and I2C, the GEM, the SD host controller); these already build for AArch64 |
| new `hardroxide-psu` | Zynq UltraScale+: AArch64 start-up and exception levels, translation tables and caches, generic timer, CRL/CRF clocks, CSU PL loading, the address map, its own interrupt controller and handler table. **Depends on `ps7` and re-exports the shared drivers** |
| portable alias | generated crates re-export their family crate as `ps7` or `psu`, and both also as `ps`, so a portable program writes `design::ps::println!` |
| `hardroxide-rt` | one scheduler; the processor port becomes `port/armv7.rs` and `port/aarch64.rs`, chosen by target |
| `hardroxide-fpga` | `slcr` stays; a `zynqmp` module beside it |
| `hardroxide-gen` | per-family templates (linker script, start-up glue, Linux files) in their own directories; one model of the design above them |
| `hardroxide-cli` | `run`, `package` and `doctor` choose the flow by family (`ps7_init` or `psu_init`, `bootgen` architecture) |
| fixtures, apps | `fixtures/rfsoc4x2/`, `apps/rfsoc4x2/` beside the Zynq ones; programs that run on both move to a shared directory only when a second family really builds them |

Where a shared driver differs in detail between the families (SD clocking, for example), `ps7` gains an additive method or parameter; if that would complicate the Zynq-7000 path, `psu` gets its own copy.

**Revised in step 0:** the plan first moved the shared drivers into a new `hardroxide-ps-common` crate and re-exported them from `ps7`. Programs would still have compiled, but `cargo-semver-checks` does not follow re-exports into another crate and reports every moved item as removed (tried with the UART driver), so the move would have switched the compatibility check off for exactly the code being moved. The cost of not moving is a name: `psu` depends on a crate named after the other family.

Found while checking, to handle when porting:

- The GEM driver hands the hardware 32-bit addresses (`as u32`). On a 64-bit processor it must refuse a buffer above 4 GB instead of truncating its address (step 4). (The SD driver moves data without DMA and has no such hazard.)
- The interrupt controller driver and handler table are fixed at the Zynq-7000's 96 interrupts; UltraScale+ has more, hence `psu`'s own (step 2).

Why the bitstream sprint comes second: the license is time-limited and the repository already treats built XSAs as fixtures, so every design the later steps need is built while the license lasts and proven with raw register access. Uncompressed bitstreams for this part are about
34 MB, so the fixtures enable bitstream compression.

**The PYNQ-Z2 regression owed by step 0 ran on 2026-11-26** (JTAG; Ethernet to the host; no card in the slot): all 15
programs of `scripts/test-board.sh` and its three network checks passed unchanged, and `ps7-smoke`, `rt-smoke` and
`net-smoke` with `net_check.py` (HTTP 14.5 MB/s, 10.7 new TLS connections a second). Loading `rt_station` with HTTPS
clients then showed 7 to 19 "bad signature" failures in each run of about 440 requests, on this branch and on 2.7.0:
**`ps7`'s interrupt entry and the Cortex-A9 context switch did not save `d16`-`d31`**, which the compiler uses to copy
memory. Checks added to both smoke programs failed on the board before the fix (199 of 200 register checks broken) and
pass after it, there and under QEMU; four loaded runs of `rt_station` then had no failure (control loop within 4 us, no
audio underrun, interrupt share unchanged). The UltraScale+ code already saved every register.
The same session showed that `net_https` and `rt_station` wrote to whatever card was in the slot; the example programs
now write only to a card named by serial number when built (checked under QEMU, not yet with a card on the board). **Maintainer's decision
(2026-11-26): no 2.7.1 and no further 2.x support**; the fix ships in 3.0.0. **Linux** ran the same
day under the PYNQ 3.1 image, DMA and HLS included ([results](../08-verification-gaps.md#board-results)); `overlay.sh`
now releases that image's own device on `IRQ_F2P[0]`. HDMI and audio were judged by the maintainer and passed, the audio
cable loopback too. The Z2's examples and tutorials were then moved to its base overlay, as the
RFSoC's are; the new programs build but are not yet run on the board. **Not run:** the SD card tests
(no spare card that day), so the card protection has not been tried with a real card.

## Step 1 results (2026-11-25)

All seven designs are built, meet timing and pass their JTAG probes on the board (104 checks; `fixtures/rfsoc4x2/README.md`). The vendor's preset gives working DDR in both address ranges. With SMA cables from the DACs to the ADCs, each DAC's tone arrives at its input at about
-15 dBFS (sent at -6 dBFS), 91 dB above the median of the spectrum, the other DAC's tone at -80 dBFS or lower; from the waveform memory and from the converter's mixer, retuned at run time. So 3.1 needs no new bitstream to have a working signal path. Unplugging a cable established the
DAC connectors: DAC A is DAC tile 2 (`vout20`), DAC B tile 0 (`vout00`); as cabled, ADC A is `vin2_23` and ADC B `vin2_01`.

Findings that later steps need:

- The interrupt controller (GIC-400) cannot be read through the debug access port, only through a core; and while it is disabled its pending registers do not show a high line (its line status registers, `GICD_SPISR`, do). `pl_ps_irq0[n]` is interrupt 121 + n, `pl_ps_irq1[n]` 136 + n.
- Connection automation leaves a dangling interconnect when two masters share a memory port, and maps only part of a large block RAM unless told its range; the build scripts do both explicitly and fail on a short memory.
- An AXI GPIO's interrupt status bits toggle when written with 1.
- The RF clock chips are programmed over the processor's SPI 0 and GPIO (MIO 7, 8, 12) from the register files in `fixtures/rfsoc4x2/clocks/`; the converter tiles need a restart afterwards.

## Step 2 results (2026-11-25)

`hardroxide-psu` and `hardroxide run` for UltraScale+ work on the board and in QEMU (`baremetal/psu-smoke`,
`scripts/test-board-rfsoc.sh`, `scripts/test-qemu-psu.sh`). On the board: 1199.999 MHz Cortex-A53 and a 33.333 MHz counter read
from the clock registers; `sleep(100 ms)` 100.006 ms; 20 timer interrupts of 10 ms in 200.17 ms; 64 MiB tested at each end of
both DDR ranges and one address bit at a time, no errors; a 64 KiB loop 60 times faster with the caches on; all 32 vector
registers intact across interrupts (the test fails if the entry omits any restore, checked in QEMU); from the PL, 10 of 10
interrupts handled and 3 of 3 waited for.

Decisions taken while building it:

- Programs run **at EL3 with no firmware**, on `SP_EL0` with exceptions on `SP_EL3`: the state after a JTAG reset, one level
  and no secure-monitor interface. Starting at another level is not supported.
- The IRQ entry saves the whole vector file: a callee preserves only half of `v8`..`v15`.
- The system counter is left to `psu_init`/the boot loader to start; its frequency is read from the clock registers.
- The AArch64 build of `hardroxide-mmio`'s physical backend now issues the same barrier as the 32-bit one before register
  writes (it did not).

## Step 3 results (2026-11-25)

The kernel's AArch64 port passes `baremetal/rt-smoke` (one program for both families) in QEMU and on the board: preemption,
periodic release, queues, interrupt hand-off, priority inheritance, registers intact across switches (the test fails when any
tried part of the restore is removed), a fault in a task reported.

**Jitter, RFSoC 4x2, two hours** (2026-11-25; `baremetal/rt-jitter` as built at `fd9d790`, board over JTAG, same load as
on the PYNQ-Z2): **0 missed releases**. Lateness of the 10 ms task over 720,223 releases: mean 0.77 us, maximum 5.94 us,
91.7 % under 1 us and none above 8 us (the earliest release 0.47 us before the baseline). Interrupt to task over 900,407
interrupts: mean 3.04 us, maximum 4.65 us. The interrupt maximum was reached in the first minute and the release maximum
in minute 45; neither grew after that. Not covered, as on the PYNQ-Z2: interrupts from the PL under load, a second master
using DDR, temperature extremes. (An earlier 65-minute run gave a maximum of 6.19 us and the same interrupt figures.)

Found and fixed:

- An interrupt or a kernel call before `start` could switch to a task and strand `main` until all tasks blocked (since 2.x).
- The AArch64 tick truncated 33,333,333 / 1000 and ran 10 ppm fast; the first benchmark counted every release as on time
  (mean lateness 0 ns). The tick now spreads the remainder, and the benchmark reports early releases.

## Step 4 results (2026-11-25)

**SD card** (SanDisk 16 GB, erased with the maintainer's permission): the guard refused builds naming no card or another card;
formatted, written and read back; the start of the card fetched over JTAG passes `fsck.fat` and the 1 MiB file matches byte for
byte; 1.8 MB/s written and 6 MB/s read in 4 KiB pieces, 11 MB/s in one 31 MiB read.

**Ethernet** (GEM 1, DP83867, cabled to a PC): 1 Gbit/s full duplex, an address by DHCP, `ping` 0.25 to 0.34 ms, all of
`scripts/net_check.py` (curl, UDP, TCP, HTTPS with curl and openssl); 18.4 MB/s over HTTP (300 kB downloads, one at a time),
220 requests/s, 21 new TLS connections/s (47 ms each, median handshake 35 ms; the Zynq-7000 managed 83 ms each).

**I2C** (read only, `baremetal/i2c-info`): bus 0 answers at the nine INA220 addresses of the board's device tree and all
nine monitors read, with their power-on configuration (rails of 0.88 to 3.39 V, about 4.4 W together); bus 1 answers at
`0x0d`, `0x30`, `0x48`, `0x50` and `0x58`, which includes the vendor's voltage DAC and identity EEPROM. The driver is the
Zynq-7000's, unchanged. Not exercised: writing a device's data (nothing on this board should be written without a reason),
and QEMU, which does not model the controllers.

Step 4 is complete for the standalone programs; the base-overlay applications wait for the generator (step 5), and those for
HDMI and audio have no hardware on this board.

**The board's own hardware** (added 2026-11-25, `baremetal/rfsoc-board`, new crate `hardroxide-board`): the identity
EEPROM, both die temperatures, the nine power monitors (through the processor's I2C), the OLED (its address counter reads
back), the LMK04828 and both LMX2594s, the processor's LEDs and button. The clock programming is confirmed by the RF
converters: after the program ran, their three PLLs locked and the loopback tones arrived at 102.375, 204.825, 307.2 and
614.4 MHz as intended. Two findings, both in the pin wired to the LMK04828's reset: the register file turns the chip's pin
into an open-drain output held low (TI datasheet, register `0x14A` = `0x06`), so the earlier probe script and a first
version of the program, which pulsed it high, drove against it (briefly; both drivers limit the current, and everything
works since); and the processor's GPIO ignores a level written to a pin while it is an input, so "write low, then enable"
drives whatever the pin last had. USB and the Pmod+ and SYZYGY connectors were left out by decision; DisplayPort, the
PL's memory and the 100 Gb port were left to the Linux examples (step 6: the memory was done, the other two dropped).

## The base overlay (2026-11-25)

**Examples and tutorials use the board's base overlay** (maintainer's decision: students should not meet a different
bitstream with each example); the step 1 designs are driver tests. `fixtures/board/rfsoc4x2_base_overlay.xsa` is
RFSoC-PYNQ 4.0.0's bitstream and handoff with a `psu_init` generated for the board preset plus the overlay's
processor-to-FPGA settings. It passes `probe.py base` on the board (LEDs, buttons, switches, the interrupt path,
temperature, Pmod memories, all four converter tiles locking, DMA resets, the PL's DDR4, which is 4 GiB mapped twice), and
Its first example drove it with the Zynq-7000's GPIO and interrupt controller drivers, unchanged (now
`apps/rfsoc4x2/baremetal/lights.rs`). Step 5's
generator and applications target it first. On the kernel, the mood light (now `apps/rfsoc4x2/rtos/rt_lights.rs`) (the overlay's interrupt wakes a
task in 3 to 4 us; a 1 ms task at most 4 us off) and `baremetal/rt-board` (the board's chips as tasks; the most urgent
within about 1 us of their times while the others take milliseconds) pass on the board. `hardroxide run` showed no console output with it, because loading takes 28 s
and the reader's time started before loading (also true of 2.x); fixed.

## Step 5 results (2026-11-25)

`hardroxide generate --platform baremetal|rtos` accepts Zynq UltraScale+ designs
([the crate](../reference/baremetal.md#zynq-ultrascale)). `hwh` reads their PL clocks, reference clock and interrupt
routes (the 16 bits `pl_ps_irq1:pl_ps_irq0` are reported through the existing `IrqRoute::Ps7`, so no public enum
changed) and picks the processing system's handoff file when an XSA holds several. The generator has a template of its own
(`baremetal_psu.rs`); register layer, drivers, HLS wrappers and examples are shared. Zynq-7000 output is unchanged
(`check-compat.py`). On the RFSoC 4x2, `Design::init` refuses an erased PL, and the generated crates of the GPIO,
interrupt controller, loopback, DMA and both HLS designs and of the base overlay pass their driver tests
(`fixtures/board_tests_rfsoc/`), interrupts on both ports included, a 40-bit DMA above 4 GiB with explicit cache
maintenance, and the kernel's example (10 ms held within 1 us).

Differences from the plan, and what is left:

- Loading the PL from the processor (planned as "PL loading") is not done: bare metal relies on `hardroxide run`, as the
  Zynq-7000 bare-metal flow relies on its loader. It comes with Linux (step 6) or with booting from SD.
- The portable name `ps` is exported by UltraScale+ crates only; adding it to Zynq-7000 crates changes their snapshots
  and waits for the first program that builds for both.
- (Closed the same day.) The DMA driver now refuses a buffer beyond the engine's address width
  (`AxiDma::with_address_width`, set by UltraScale+ crates from the design's `c_addr_width`, which is part of their
  interface hash; a Zynq-7000's is unchanged), reported as the existing `MmioError::BadAddress` because a new variant
  would break compatibility; and the base overlay's two examples are applications on generated crates
  (`apps/rfsoc4x2/`).
- A network application on the kernel.

## Step 6: Linux (verified on the board except the radio; 2026-11-25)

Read from the PYNQ 4.0.0 image without booting it: kernel 6.12.40-xilinx with the `zynqmp-fpga` manager, device-tree
overlays, unrestricted `/dev/mem`; `uio_pdrv_genirq` loaded at boot with `of_id=generic-uio`; the device tree has symbols
(`&gic`) and **already a UIO node `fabric` on `pl_ps_irq0[0]`** (SPI cell 89); a 512 MiB CMA pool below 2 GiB;
`u-dma-buf` absent but `gcc`, `make` and the kernel's build directory present.

Decisions: DMA memory stays `u-dma-buf`, built on the board as for the Zynq-7000 (no new buffer backend; the kernel's
DMA heaps would need cache maintenance and address lookup from user space). A design's line on SPI cell 89 is served by
the image's `fabric` node (generated lines take its name and the overlay omits them). Loading follows PYNQ: the
`fpga_manager`, then the port widths, which the boot loader set for another design.

Done: `hardroxide-fpga::zynqmp` (PL clocks, port widths, loader with this family's PL addresses),
`BitFile::to_bin_zynqmp` (byte-identical to `bootgen -arch zynqmp` for the base overlay), and the Linux crate for
UltraScale+ designs (from the same templates; the Zynq-7000 output is unchanged). Checked without a board: unit tests
natively and as AArch64 binaries (`scripts/test-aarch64.sh`); every RFSoC design's crate type-checks for
`aarch64-unknown-linux-gnu`; the base overlay's crate loads against mock registers and sets the expected ports and clocks;
the interrupt overlay merges onto the image's own `system.dtb`; cross-built programs need glibc 2.34 (the image has
2.39).

**On the board** (PYNQ 4.0.0, programs run as root from memory, `fixtures/board_tests_rfsoc_linux/`): the base overlay
and the `gpio`, `intc`, `loopback`, `dma`, `hls_vadd` and `hls_scale` designs passed `board_check` (load, PL clocks
within 1 %, interrupt devices) and their programs: LEDs and GPIO read back; 100 interrupts through the base overlay's
controller; the Pmod memories; UART, I2C, SPI, FIFO, timer and block RAM of `loopback` with its eight interrupt lines;
100 calls of `vadd` ending in interrupts; both DMAs (1 MiB, then 500 short transfers with new data, three runs, an
interrupt for each of the 6,012 channel completions) and `scale` on `u-dma-buf` buffers. The kernel logged no faults.

Found on the board and fixed:

- This kernel names UIO devices after the node **with** its unit address (`fabric@A0000000`), so a line was found only
  when exactly one device had its block's address; the shared line of the base overlay was not. `find_uio` now also
  accepts the name before the `@`.
- `u-dma-buf` maps an `O_SYNC` buffer as *device* memory on AArch64: an ordinary copy to an odd offset ended the program
  with a bus error (reproduced before the fix). `Udmabuf` now selects the module's write-combining mode, and the Linux
  register backend gained the barriers that normal memory needs (`dsb sy` before a write, `dsb ld` after a read).

Limits met: a line keeps its first trigger type until a reboot (`loopback` declares SPI cell 90 edge-triggered, `dma`
level), and `board_check` does not notice, since the device still opens. `u-dma-buf` builds on the board (the image lacks
`bc`; pass the kernel's version suffix); it was loaded for one boot at a time, never installed.

Tutorials 8 and 9 (`apps/rfsoc4x2/linux/`, run with `scripts/board/run.sh`, which now builds for AArch64 too): the
base overlay's lights and interrupts as a Linux program, and a web page serving its inputs, LEDs, temperature and the
nine power monitors (through the kernel's drivers; 12.5 W in sum, as on bare metal), checked from the host over the
network and through an SSH tunnel. The maintainer then checked both by hand: 20 button presses, each registered once,
the switches, the colours, and the page in a browser. `scripts/board/overlay.sh` unbound the image's `fabric` device when replacing an
overlay, until the next boot; it no longer does, and takes a compiled overlay since the image has no `dtc`.

Tutorial 10, `pl_memory`: the FPGA's DDR4 from Linux, 30 address lines, 12 MiB of patterns at the start, middle and
end, 19.1 MB/s writing and 15.1 MB/s reading a word at a time. Its reference clock is an output of the LMK04828 (board
manual), which the image's `boot.py` programs with the same register values as ours; the program refuses to touch the
memory unless that service has succeeded. That script also loads the base overlay about 90 s after power-on, replacing
anything loaded earlier.

Not done: the radio blocks and the base overlay's DMA engines; `hardroxide doctor` for this family. **DisplayPort and
the 100 Gb port are dropped from the examples** (maintainer, 2026-11-25: nothing to test them with). The bare-metal register backend now also completes a read before later accesses on AArch64 (`dsb ld`), as the Linux one
does.

**The kernel's network program** (`apps/rfsoc4x2/rtos/rt_dashboard.rs`, tutorial 7): the base overlay's page served by a
priority-3 task beside a priority-5 control loop. On the board: 10,742 requests from four clients in 20 s, none failed,
the 10 ms loop within 1 us throughout.

**Full board test after both** (`HRX_NET=1 scripts/test-board-rfsoc.sh`, without the SD card test): everything passed but
one check in `rfsoc-board`, which expects the DAC's synthesizer to report no lock while the LMK04828 is reset and read
"locked"; both synthesizers locked once it was programmed. Six repeats straight afterwards, three with the new read
barrier and three without, all reported no lock, so the barrier is not the cause. The failing run was the first access
to the clock chips since the board was switched on, after a Linux session. After a later power cycle (2026-11-26, JTAG
mode), `rfsoc-board` run first reported no lock and passed, so being the first access is not enough to cause it; a
preceding Linux session was not repeated. The cause is **unknown** (one failure in eight runs); the check is unchanged.

**Retest before the release** (RFSoC 4x2, 2026-11-26, `v3` at `6da3514`, after the PYNQ-Z2 work):

- JTAG: `HRX_NET=1 scripts/test-board-rfsoc.sh` passed, the clock-chip check included; the SD card test was not run.
  HTTP 16.23 MB/s and 227 requests/s, HTTPS 22.1 handshakes/s; the kernel's web page answered 500 of 500 requests, the
  10 ms loop within 1 us. `rf_loopback` with the cable passed, with the levels of 2026-11-25.
- Linux (PYNQ 4.0.0; programs run from the board's memory, nothing installed): `board_check` and the test program of all
  seven designs the Linux tests cover passed, with the current `overlay.sh` and `hardroxide-irq`. DMA 1 MiB there and
  back in 2.8 ms and 0.74 ms; the FPGA's DDR4 19.0 MB/s writing, 15.0 reading; the base overlay's dashboard answered 200
  of 200 requests on the board itself. The buttons and LEDs were not checked by hand (skipped by the maintainer).
- **Once, the board's Ethernet did not come up**: on the first start from the SD card after the JTAG run, Linux ran for
  over an hour with `MDIO device at address 15 is missing` and `Could not attach PHY (-19)`, and the PC saw no link. It
  came up on each of the next two starts (a restart by the maintainer, then a `reboot`). The cause is **unknown**.

## Risks

| Risk | Mitigation |
|---|---|
| License expires before a design is right | build early; keep build scripts in the repository; a permanent license (check whether the kit includes a voucher) |
| Wrong DDR settings damage nothing but make everything fail strangely | take the PS preset from the board vendor or the board's PYNQ design; memory test first |
| The RF design cannot be fully checked before the 3.1 driver exists | check clocks and register access over JTAG; compare with the PYNQ base overlay, whose prebuilt bitstream is also usable |
| RF input damage | confirm the DAC output level and the ADC's limit in the board documentation before connecting a loopback cable, with an attenuator if needed |
| The PYNQ-Z2 is unavailable | the host checks and QEMU still run; no milestone is declared Zynq-compatible on hardware without the board |
| Writing the wrong SD card | the card is identified by serial number and confirmed before the first write, and the existing format guard stays |
| Security-sensitive code (network, TLS, crypto) is carried to a new architecture | the same test vectors and interoperability tests run on AArch64; constant-time properties are not assumed to carry over |
