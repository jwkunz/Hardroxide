# Applications 4: An SD card and files

**Design:** `fixtures/board/pynq_base_overlay.xsa` · **Needs:** [Applications 1](01-base-lights.md), a microSD card **that you can erase** in the board's slot (JTAG boot mode, so nothing boots from it)

> **Status: run on a PYNQ-Z2 (2026-11-21)** with a 32 GB SDHC card: initialisation, raw transfers, formatting, 9 files verified byte for byte, a data logger, WAV playback from the card and a screenshot saved
> and reloaded all work. Not independently checked: the card formatted by the board has not yet been through `fsck.fat` on a PC (the same code did pass `fsck.fat` on images written under QEMU).
> The first run found a board configuration bug (section 6) and a decoding bug (section 7).
> The rule that a program writes only to a card named by serial number (sections 3 and 4) is newer than that run: tried
> under QEMU, not yet on a board.

The Zynq's own SD controller (SD0, the slot on the PYNQ-Z2) is driven by [`ps7::sd`](../../reference/ps7.md#sd-card-controller) in programmed I/O and implements the
[`BlockDevice`](../../reference/mmio.md#block-devices) trait; [`hardroxide-fat`](../../reference/fat.md) is a FAT32 file system over any block device. Neither knows about the other.

## 1. The pieces

| Piece | Where | What it does |
|---|---|---|
| `SdHost` | [`hardroxide-ps7`](../../reference/ps7.md#sd-card-controller) | identifies the card, 4-bit bus at 25 MHz, reads and writes 512-byte blocks |
| `BlockDevice` | [`hardroxide-mmio`](../../reference/mmio.md#block-devices) | the one trait between them |
| `Volume`, `File` | [`hardroxide-fat`](../../reference/fat.md) | mount, long names, directories, read, write, append, format |
| `gfx::bmp` | [`hardroxide-gfx`](../../reference/gfx.md#bmp-files-gfxbmp) | BMP files, row by row |

## 2. Look at a card without changing it

```console
$ hardroxide generate fixtures/board/pynq_base_overlay.xsa --platform baremetal -o work/base --hardroxide-path . --name design_1
$ cd work/base
$ cargo add --dev --path ../../crates/hardroxide-fat
$ cp ../../apps/base/baremetal/sd_info.rs examples/
$ cargo build --release --example sd_info
$ hardroxide run target/armv7a-none-eabihf/release/examples/sd_info --xsa ../../fixtures/board/pynq_base_overlay.xsa --watch 30
```

`sd_info` only reads. On a 32 GB SDHC card that came with a firmware update file on it:

```console
== sd_info (SD base clock 50000000 Hz) ==
card detect pin: card present
card: 61521920 blocks = 30040 MiB, SDHC/SDXC, manufacturer 0x02, product "SA32G", serial 0x2df43e3b, bus 25000000 Hz
FAT32: 28994 MiB free of 30028 MiB, clusters of 32768 bytes
  d          0  UPDATE
  UPDATE/
      - 1083563520  PS4UPDATE.PUP
```

That is a file system someone else formatted, read by this project's FAT code. The manufacturer, product name and serial agree with what Linux reports for the same card
(`/sys/block/mmcblk0/device/`), which is the check that caught the bug in section 7.

```rust,ignore
let mut sd = SdHost::new(be.map(ps7::map::SDIO0_BASE as u64, ps7::map::SDIO_SIZE).unwrap(), base);
let info = sd.init().unwrap();                 // identification, 4-bit bus, 25 MHz
let mut vol = Volume::mount(sd).unwrap();      // the card is now a file system
vol.read_dir("/", |e| println!("{} {}", e.size, e.name)).unwrap();
```

## 3. Format it and test it (this erases the card)

`sd_erase_and_test` **runs only on the card you name.** Give its serial number (the one `sd_info` prints) when building; any
other card, blank or not, is left untouched:

```console
$ cp ../../apps/base/baremetal/sd_erase_and_test.rs examples/
$ HRX_ERASE_SERIAL=0x2df43e3b cargo build --release --example sd_erase_and_test
$ hardroxide run target/armv7a-none-eabihf/release/examples/sd_erase_and_test --xsa ../../fixtures/board/pynq_base_overlay.xsa --watch 150
```

```console
== sd_erase_and_test: THIS ERASES THE CARD ==
card: 30040 MiB, SDHC/SDXC, bus 25000000 Hz, serial 0x2df43e3b
the card's serial number was confirmed by its owner as erasable: proceeding
raw blocks: 1, 4 and 64 block transfers verified at the end of the card
formatted in 15347 ms
FAT32: 30024 MiB free, clusters of 16384 bytes
9 files from 0 to 100000 bytes written and verified byte for byte
4 MiB: write 2530 ms (1618 KiB/s, includes filling the buffer), read 542 ms (7555 KiB/s)
SD TEST OK
```

Raw transfers of one, four and 64 blocks are checked first, then the card gets an MBR with one FAT32 partition and nine files from 0 to 100000 bytes (sizes at the edges of a sector
and a cluster, plus a nested directory with a long name) are written and compared byte for byte. The speeds are programmed I/O (the processor moves every word through the controller's
data port): read about 7.4 MB/s, write about 1.6 MB/s (the write figure includes generating the data and the card's own programming time). DMA through the controller's ADMA would be faster; it is not used.

## 4. Applications that use the card

Each needs a card formatted by the step above (or any FAT32 card; they add files and never format). **Writing needs your
leave, card by card:** name the card's serial number when building, with its own variable:

```console
$ cp ../../apps/base/baremetal/sd_logger.rs examples/
$ HRX_WRITE_SERIAL=0x2df43e3b cargo build --release --example sd_logger
```

Without it (or with another card in the slot) `sd_logger` and `sd_bmp` refuse and write nothing, and so does `sd_wav` if
the card has no `/chime.wav` yet; a card that has one is played without being written. `info.serial_matches(..)` is the
check, for programs of your own.

| Program | What it does | Result on the board |
|---|---|---|
| `sd_logger` | appends ten timestamped lines to `/LOG.TXT` per run, reads the file back and checks the new lines follow the old | 10 lines in run 1, 20 in run 2 (a separate boot): `SD LOGGER OK` |
| `sd_wav` | writes the built-in chime to `/chime.wav` if the card has none, loads the file into RAM, parses it and plays it twice (put your own 16-bit WAV there from a PC) | 32044-byte file, 2 s, 0 samples missed: `SD WAV OK` |
| `sd_bmp` | draws a picture on the HDMI output, saves it as `/screen.bmp`, blanks the screen, loads the file back onto the screen and compares every pixel | 2,764,854 bytes saved in 9.7 s, loaded in 2.4 s, 0 pixels differ: `SD BMP OK` |

```console
== sd_logger ==
/LOG.TXT has 10 lines: this is run 2
/LOG.TXT now has 20 lines, 480 bytes
last line: run 2 line 9 at 4095 ms
SD LOGGER OK
```

```rust,ignore
let mut f = vol.open("/LOG.TXT", OpenMode::Append).unwrap();
f.write(&mut vol, b"a line\n").unwrap();
f.close(&mut vol).unwrap();          // the directory entry now has the new size
vol.sync().unwrap();                 // everything on the card before it is removed
```

The `.bmp` is a plain 24-bit bottom-up BMP (the format the decoder in `gfx::bmp` and its host tests follow; it has not yet been opened in a PC image viewer). The saving takes longer than the loading because each row is converted from the (non-cacheable) frame buffer and written as its own 3840-byte transfer.

## 5. Safety

An SD tool that formats a card is dangerous on a card you did not mean. The first version of `sd_erase_and_test` ran on a card in the slot that turned out to hold a working PYNQ image (it read "no
FAT32 file system" and was taken to be blank), and it was stopped part way: that card's partition table and boot partition were overwritten and it had to be re-flashed. Because of
that, and because other programs of the series wrote files to whatever card they found, every write now needs the serial number: the owner says *this* card, not "whatever is in the
slot". A card that holds anything you care about should be read with `sd_info` only.

## 6. The board needed 1.8 V on MIO bank 1

The first run on a card failed at the first command: the controller reported a *command conflict* with a timeout on every command. The configuration came from the board preset: the PYNQ-Z2 powers **MIO bank 1 (pins
16 to 53: Ethernet, USB, the SD card)** at 1.8 V and bank 0 at 3.3 V, and the preset had both at 3.3 V, so `ps7_init` set the SD pins' I/O type to `0x1680` (3.3 V). Reading the Linux image's
registers over JTAG (`MIO_PIN_40` to `MIO_PIN_45` were `0x1280` there) showed the difference. The preset now carries `PCW_PRESET_BANK0_VOLTAGE` and `PCW_PRESET_BANK1_VOLTAGE`, and every board build
script was regenerated. This matters beyond the SD card: the Ethernet PHY (RGMII) is on the same bank.

## 7. The identity was one byte off

`sd_info` printed `product "MSA32"` and serial `0x112df43e` for a card that Linux calls `SA32G`, `0x2df43e3b`: the CID's fields were taken one byte too early (the controller presents bits 127:8 of the register, with the CRC byte dropped).
It was cosmetic until the erase guard compared the serial; a unit test of the field layout now pins it, and the output above agrees with Linux.

## 8. What did not work, and what is not covered

- A Netac 8 GB microSD HC card did not answer commands on the board and did not appear in a PC's card reader either: a card or adapter fault, not the driver.
- Not run: standard-capacity (SDSC) cards, the 1-bit bus, the second controller (SDIO1), hot removal during a transfer, UHS cards, writing from the RTOS flavor, and FAT file systems larger than 32 GB or made by other tools than the two checked here (`mkfs.fat`, this crate).
- The files written by the board were verified by the board's own reads, not yet by `fsck.fat` on a PC.
